# 0013. Generic code kept in YPhoenix and YexBlockNote, not published

- **Status**: Accepted
- **Date**: 2026-10-13 (YPhoenix), 2026-10-28 (YexBlockNote)

## Context

Two parts of Padocs are not specific to it: syncing Yjs documents over
Phoenix channels, and reading BlockNote documents from their Yjs state.
Either could become a library complementing y_ex, but their APIs are not
settled.

## Decision

- `lib/y_phoenix` (`YPhoenix.DocServer`, `Channel`, and the `Persistence`,
  `Presence` and `Access` behaviours) refers to nothing in Padocs; the
  application injects its modules.
- `lib/yex_block_note` exposes only the `YexBlockNote` facade (`to_blocks`,
  `empty?`, `to_text`, `to_markdown`, `to_typst`). Only
  `YexBlockNote.Blocks` calls Yex, turning the fragment into plain maps close
  to BlockNote's blocks; the renderers read only those.
- Neither is published for now: decouple in the repository first, upstream
  the generic bits to y_ex, publish once the API holds.

## Consequences

- Padocs' roles, fragment name and excerpt policy stay in `Padocs`.
- Couplings still to remove from YPhoenix: the hard dependency on :syn, the
  shutdown driven by Phoenix.Presence.
- A published YexBlockNote would need fixtures generated by
  `@blocknote/core` to catch schema changes.
